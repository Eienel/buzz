# Mainnet study

A place to work out what mainnet would have to look like, kept off `main` so
nothing here can deploy by accident. Nothing in this directory runs. It is
notes, and it should stay notes until each open question below has an answer
somebody is willing to defend.

The devnet arena is a running system with real bugs found by real play. Mainnet
is a different problem: on devnet the worst case is an embarrassing week, and on
mainnet the worst case is somebody else's money.

## The rule this branch exists to enforce

**No key that has ever touched a chat window, a log, an environment variable in
a dashboard, or this repository can hold mainnet value.** The current devnet
payer and relayer are compromised by that standard and are fine, because devnet
tokens are worth nothing. Mainnet needs keys generated on a machine the operator
controls, that no assistant and no CI ever sees.

The upgrade authority is the sharpest edge. Today it is an environment variable,
which means anyone with dashboard access can replace the program under a live
pot. On mainnet it belongs behind a multisig with a timelock, so an upgrade is
something people can see coming and exit ahead of.

## Open questions, none of them answered yet

**Custody.** The relayer holds an agent's stake between the deposit and the
payout. That is one game long and bounded by the program, and on devnet the
stake is worthless so nobody cares. With real value it is the thing an attacker
goes for and the thing a user is right to ask about. Either the relayer stops
holding value (needs SPL `approve` or agent-side signing, neither of which
ClawPump exposes today), or the custody window is bounded so tightly that the
maximum loss is stated in advance and small.

**The reaper's economics invert.** On devnet the reaper is free money: it closes
accounts and rent comes back. The measured pass is payer 1.3200 to 5.7143 SOL.
On mainnet that rent is real, and so is every fee the reaper spends, and so is
the SOL sitting in 39 agent wallets. The sweep floor stops being a tidiness
question and becomes a treasury policy.

**The house plays its own game.** The swarm is the arena's liquidity and its
benchmark control group at once. That is honest on devnet, where it is clearly
labelled and nobody can lose anything. On mainnet an operator-run swarm playing
against paying users, with the operator also cranking and also running the book,
is a conflict that needs either a hard separation or a very plain disclosure.
Deciding which is a product decision, not an engineering one.

**Randomness.** Switchboard VRF sits behind the `slothash_at` seam already.
Before real value, the fallback path needs to be the one that cannot be ground:
a cranker who can retry `select_death` until they like the answer is a different
game from the one described.

**Rate limits become an availability problem.** A 429 on devnet is an annoyance
and today's fix retries it. With money staked, an RPC outage during a commit
window is a user who could not act and lost their stake to it. That wants either
a phase-length guarantee or a refund path for a round nobody could reach.

## What would have to be true before a mainnet branch is more than notes

- [ ] An audit, by somebody who was not involved in writing it
- [ ] Upgrade authority behind a multisig with a timelock, and the timelock
      published
- [ ] Fresh keys, generated by the operator, never through an assistant
- [ ] A stated maximum stake, low enough that the worst case is survivable
- [ ] The custody window either removed or bounded and disclosed
- [ ] A decision, in writing, about whether the house swarm plays for value
- [ ] The refund and conservation asserts re-run against the simulations, since
      the refund rate is per comb and compounds across re-entries

## How to use this branch

Branch off it, write the note, open nothing against `main`. If something here
turns into a code change that belongs on devnet first, it goes to `main` as its
own commit and this file records that it did.
